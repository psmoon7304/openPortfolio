BE 4가지 가치
04 BE 에서 가장 신경 쓰는 4가지
My BE Principles

1. 동작 신뢰성 — Reliability

"이 코드가 동작한다 ≠ 의도한 대로 동작한다"
  • WebSocket SockJS Fallback 사건 — 101 OK 만 보고 안심하지 않고, 실제 transport 끝까지 검증
  • Jenkins SHA 검증 단계 도입 — 빌드 성공 ≠ 배포 반영을 파이프라인이 직접 검증
  • 회원 탈퇴 cascade 정리 — try-catch 로 덮지 않고 연관관계 주인을 다시 그림
  • 사용자 임베딩 NULL 사고 — 저장과 조회 사이 타입 매핑 책임 지점 추적

2. 빠른 응답성 — Responsiveness

"사용자 응답 시간을 부수효과로 만들지 않는다"
  • Kafka 비동기 분리 — 추천 벡터 계산을 사용자 응답 경로에서 분리
  • Docker Multi-stage Build — 이미지 1GB+ → 슬림 JRE 베이스
  • Docker 레이어 캐싱 — Gradle 의존성과 소스 레이어를 분리
  • DLT 헤더 기반 추적 — 실패 메시지 보존 + 본 흐름 차단 X

3. 데이터 보안성 — Security

"인증·권한은 코드 리뷰가 아니라 기능 구현 단계에 있어야"
  • 음원 파일 접근 권한 누락 발견 — Nginx 통과 후 owner 검증 누락 케이스
  • GitHub Webhook HMAC-SHA256 서명 검증 — 외부 신뢰 경계를 첫 줄에서
  • JWT 인증 풀스택 책임 (BLUEFOX) — OAuth → AT → 내부 JWT 발급/검증
  • JWT 파싱 실패 폴백 처리 — 관측이 본 흐름을 절대 막지 않도록

4. 리소스 효율 — Resource Efficiency

"같은 결과라면 더 적은 리소스로"
  • 벡터 저장소 통합 — Qdrant 별도 운영 대신 PostgreSQL 한 곳으로
  • Docker Multi-stage + 레이어 캐싱 — 이미지 1GB+ → 200MB 대
  • 추론 컨테이너 로컬 분리 — FastAPI / Qdrant 를 로컬로 분리해 비용 절감
  • 컴포넌트 1개 감축 — 운영해야 할 인프라 면적 자체를 줄이는 접근

DrawRun · Trouble 01
DRAWRUN · TS 01 트랙 캡처 정합성
표시용 좌표 vs 계산용 좌표 분리

"트랙 캡처가 직선으로 찍히던" 사건

문제 에디터의 다익스트라 경로는 두 점만 찍어도 도로를 따라가는 곡선이 나왔는데, 트랙 스냅샷에는 두 점을 잇는 직선 폴리라인이 박혔습니다. 화면에서 보이는 경로와 캡처로 저장·공유되는 경로가 달랐습니다.
해결 스냅샷 모듈이 받는 좌표를 "사용자가 찍은 원본 점" 에서 다익스트라 결과 routeCoords 로 교체. 표시 · 계산 · 캡처가 같은 좌표를 공유하도록 정리.
결과 두 점만 찍어도 도로를 따라가는 폴리라인이 스냅샷·랭킹 미리보기에 일관되게 반영. "사용자가 보는 경로" 와 "캡처로 저장되는 경로" 의 시각적 불일치 해소.
핵심은 "화면에 그려지는 좌표 = 캡처에 박히는 좌표" 라는 가정을 의심한 것. 같은 도메인 안에서도 데이터가 흐르는 경로가 다르면 결과가 다릅니다.

DrawRun · Trouble 02
DRAWRUN · TS 02 공유 상태 reset 의 책임 경계
Riverpod · 의미 단위 책임 분리

"카운트다운 진입 직후 폴리곤 가이드가 사라지던" 통합 버그

문제 챌린지 "바로 시작" 으로 카운트다운에 진입한 직후, 폴리곤 가이드 이미지가 사라지는 버그. 원인은 resetMeasurementsForNewSession() 이 측정값뿐 아니라 polygonImageUrl 까지 함께 리셋한 것 — reset 의 책임 경계가 모호해서 의미가 다른 두 상태가 한 함수에서 같이 비워지던 사고.
해결 함수의 책임을 "이 세션 동안만 의미가 있는 측정값" 으로 좁히고, 세션 경계를 넘어 유지돼야 할 필드는 reset 대상에서 명시적으로 제외. 시그니처와 docstring 으로 reset 범위를 코드 안에 박아둠.
결과 카운트다운 진입 직후에도 폴리곤 가이드가 그대로 표시. "reset 함수는 비울 대상의 의미 범위를 함수 이름으로 드러내자" 가 팀 컨벤션으로 정착.
책임 경계는 "기능"이 아니라 "데이터 의미 단위" 로 그어야 한다는 점을 배운 사건.

The Interview · Trouble 01
THE INTERVIEW · TS 01 Jenkins SHA 검증 파이프라인
"빌드 성공 ≠ 배포 반영" 을 파이프라인이 직접 검증

"빌드는 성공인데 배포가 안 된 것 같다" 가 반복

문제 BE 변경이 있을 때마다 사람이 컨테이너를 직접 떨궈서 재기동하는 운영은 한계. "이미지가 새 SHA 인지" 를 매번 사람이 확인해야만 배포 반영이 보장되는 구조였습니다.
해결 GitLab Webhook 수신 → BE 변경 감지(git diff) → Unit Test → CI build → CD deploy → SHA 검증 5단계 파이프라인으로 통합. 현재 컨테이너 이미지 SHA 와 :latest SHA 를 inspect 로 비교해 일치하지 않으면 재배포, 일치하면 배포 완료 처리.
결과 GitLab 의 빌드 상태가 "실제로 그 이미지가 떠 있는지" 까지 의미하게 됨. BE 변경 → 배포 완료까지 사람이 끼지 않고도 신뢰 가능.
파이프라인의 가치는 "자동으로 돌아간다" 가 아니라 "의도한 상태인지 자신이 확인까지 한다" 에 있다는 걸 정리한 사건.

BLUEFOX · Trouble 01
BLUEFOX · TS 01 OAuth → 내부 JWT 발급 흐름
외부 GitHub Token 을 서버 내부에 격리

GitHub Access Token 을 절대 클라이언트에 보내지 않는다

문제 GitHub OAuth 의 Access Token 을 그대로 클라이언트에 노출하면, 외부 토큰이 곧 우리 서비스의 인증이 되어 책임 분리가 안 됨.
해결 Spring Security 가 code → AT 교환을 받자마자 OAuth2SuccessHandler 에서 내부 JWT (Access + Refresh) 를 발급하고, UUID 키로 TokenCache 에 저장한 뒤 프론트에는 uuid 만 던져줍니다. 프론트는 GET /token/{uuid} 로 내부 JWT 만 받아가고, GitHub Token 은 서버 내부에서만 사용.
결과 외부(GitHub) 인증과 내부(BLUEFOX) 인증이 책임 단위로 분리. 이후 모든 요청은 내부 JWT Bearer 하나만으로 처리되고, 외부 토큰은 서버 내부에 격리됩니다.

사용자 응답과 추천 계산의 책임 분리

사용자 응답 경로에서 추천 계산을 떼어내고, 실패는 잃지 않기

문제 사용자가 기사를 클릭하는 순간 추천 벡터를 갱신해야 하지만, 그 계산이 응답 시간에 끼면 API 가 무거워짐. 또한 갱신이 실패해도 사용자 흐름은 끊기면 안 되고, 동시에 실패 메시지를 잃어서도 안 되는 요구.
해결 @CollectLog 어노테이션 + AOP 로 GET 요청을 가로채 log-interaction 토픽으로 비동기 발행. Logging Server 의 컨슈머가 처리, 실패 시 5회 / 30초 간격 재시도 후 모두 실패하면 log-interaction.DLT 로 옮기고 DeadLetterEventListener 가 실패 로그를 영구 기록.

NEWSTAGRAM · TS 03 사용자 임베딩 NULL 사고
저장과 조회 사이의 진짜 책임 지점 찾기

"저장은 됐는데 조회가 NULL"

문제 설문 후 사용자 임베딩을 분명히 저장했는데, 로그인 시점의 조회 결과가 매번 NULL. 저장 SQL 은 정상이었고 DB 에도 값이 들어가 있었음. 저장과 조회 사이의 어디에선가 타입이 깨지고 있다는 가설로 추적 시작.

세 가지 안(String 수동 파싱 / 외부 라이브러리 / AttributeConverter) 중 "도메인 코드가 그대로 유지되며 다른 컬럼에도 재사용 가능" 을 기준으로 선택한 사건.
